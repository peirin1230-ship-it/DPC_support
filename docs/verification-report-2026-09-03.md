# DPC検索ツール 検証報告書（2026年9月3日）

対象リポジトリ: `peirin1230-ship-it/DPC_support`（検証開始時点のコミット `bb14959`、修正反映後 `077ba46`）
対象データ: 令和8年度 DPC電子点数表 `database/001737745.xlsx`（有効期間の基準日 2026-08-13、3,267 DPC・504 分類）

本書は次の3つの問いに答えるために実施した検証の結果をまとめたものです。

1. このシステムは実証（現場での試行・評価）に耐えうるか
2. 医事課職員や現場の医師がコーディングをするうえで便利な機能はほかにないか
3. 現状の設計がベストなのか

## 0. 結論（要約）

| 問い | 結論 |
|---|---|
| 実証に耐えうるか | **条件付きで「耐えうる」**。点数表データと判定ロジックは一次資料（保医発0321第6号・コーディングテキスト第6版・電子点数表前提条件）と整合し、全3,267 DPCに対するプロパティテストで不一致はゼロ。検証で見つかった致命的・重大な不具合（サジェストで159分類が必ず0件、変換テーブル縮約の未反映、「下から優先」違反 など）は本検証の中で修正し、回帰テストを追加した。ただし現状は「候補を探す参照ツール」であり、「1患者1回の操作で確定DPCと根拠を出す」コーディング支援としては、複数入力の一括判定・副傷病自動判定・入院日ベースの期間計算・判定根拠の提示が無い。現行フローとの所要時間・誤り率比較を目的とする実証には、これら P0 機能の実装が前提になる。 |
| 便利な機能はほかにないか | 医事課・医師・設計の3視点から **合計 40 件超の提案**を整理し、優先度 P0〜P3 に格付けした（第7章）。P0 は「複数入力の一括判定」「定義副傷病の自動判定」「入院日・退院日入力と期間境界の暦日表示」「判定根拠パネル（摘要欄向けテキスト出力）」「DPCコード逆引き」。 |
| 現状の設計がベストか | **概ね妥当（設計批評の総合評価 4/5）**。維持すべきは「単一HTML配布（file:// でも動作）」「純関数のロジック層」「Excel→data.js の再生成一致検証とCI」。変えるべきは「基準日1点のスナップショットで年度・月次の切替ができない」「`D` シングルトンで複数データセット・テスト用データを差し替えられない」「DPCTool.jsx への状態集中」「UI・E2E テストの不在」。 |

### 1-1. 一次資料

### 7-6. 医師視点の所見（要約）

- **病名入力が最大の障壁**だった。臨床用語216語のうち92語（43%）が候補0件、候補が関連度順でなく主要な外傷コードが出ない、略語が無関係な部分一致を返す、候補未選択の Enter で「一致なし」、ドット付き ICD が不一致。→ 本検証で別名辞書・表記ゆれ吸収・関連度順・ドット対応・自動採用を実装（未ヒット語 39語の再測定で 35語がヒット）。症状語の案内（A9-05）と医療資源病名チェック（A9-06）は P0/P1 に残る
- **説明性**: 「２あり」「あり」といった桁ラベルだけでは医師が妥当性を確認できない。判定経路と代表行為名（例: ２あり＝脳血管疾患等リハビリテーション）の表示が必要（P0 判定根拠パネルに統合）
- **伝達**: 医師が確認した DPC と根拠を医事課へ伝える手段が無い（コピー・印刷・URL）。P0 のコピー機能で最小対応、URL・印刷は P1
- **モバイル・短時間操作**: サジェスト検索後の結果遷移と入院日数必須は本検証で修正。副傷病ステップの ICD 検索（A9-08）は P1
- **教育**: 14桁の桁解説・期間・相関値をアプリ内で学べる導線が無い（P1）

## 8. 設計評価（現状の設計はベストか）

設計批評（A7）とアーキテクチャ監査（G4）の結論は「参照ツールとしての現行設計は妥当（4/5）。ただし年度・データセットの単一性と状態集中が拡張の壁」である。

### 8-1. 維持すべき点

| 単一HTML配布（Vite + vite-plugin-singlefile） | `dist/index.html` 1ファイルを `file://` で開いても外部通信ゼロで 0.18秒で起動、絶対パス参照0件。院内ファイルサーバ・USB 配布がそのまま成立する。Electron・院内サーバ・外部JSON fetch は不要 |

| Excel → `data.js` の決定的生成 ＋ `validate:data` ＋ CI | 「公式点数表と一致している」ことを機械的に保証する、点数表ツールとして最も重要な性質 |
| node:test によるデータ不変条件テスト | 特定コードをハードコードせず改定後もそのまま使える |

### 8-3. 採用しない選択肢
- **Electron 化**: 配布サイズ 100MB 超、署名・更新配信の運用負荷。ローカル保存や外部連携が無い本ツールには利点がない
- **院内サーバ／API 化**: 単一HTMLを置くだけで足りる。バックエンドが無いことは監査・セキュリティ面でも利点
- **PWA**: 公開URL 利用者から要望が出た時点で、更新バナー付きで導入（Service Worker は file:// で動かず、旧キャッシュ残留は点数表ツールでは事故要因）
- **Tailwind / CSS-in-JS**: 規模に対して過剰。CSS Modules で十分
- **Zustand / Redux**: 状態階層が浅く導入理由が弱い
